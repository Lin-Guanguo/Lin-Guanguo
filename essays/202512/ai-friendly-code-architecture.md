# AI-Friendly Code Architecture

我现在编码过程中遇到的问题、思考，都会和 GPT5 讨论，ChatGPT 现在有跨对话的记忆，我发现我问的越多，AI 好像越懂我了。

## 这是我和 ChatGPT 的一段对话

## 问：AI-Friendly Code Architecture 总结一下方法论

下面给你一套**可总结、可传播、可落地**的
**AI-Friendly Code Architecture（面向 AI 的代码架构）方法论**。
这是在你当前实践背景下（AI 写代码 + 多 Agent + 自动化测试 + DevOps）的**抽象归纳版**，不是具体技术清单，而是**设计哲学 + 约束体系**。

---

## 一、核心定义（一句话）

> **AI-Friendly Code Architecture**
> 是一种**以“可被 AI 正确理解、正确修改、可验证执行”为第一目标**的代码与系统架构方法，而非以人类开发体验为唯一中心。

这意味着：

* 不是“AI 能写”，而是**AI 不容易写错**
* 不是“一次生成”，而是**可反复迭代、可回归验证**
* 不是“聪明设计”，而是**低歧义设计**

---

## 二、三大设计公理（非常关键）

### 公理 1：**最小歧义原则（Minimum Ambiguity）**

> 任何需要 AI 推理的地方，都应当尽量变成**显式结构**

**典型做法**

* 强类型 > 约定 > 注释
* 枚举 > 魔法字符串
* 显式状态机 > 隐式流程
* 明确输入输出边界 > “上下文推断”

**反模式**

* “这个函数顺便会做 X”
* “根据调用场景不同，行为不同”
* “这里默认你知道前面发生了什么”

---

### 公理 2：**流程可冻结原则（Flow Freezable）**

> AI 擅长**探索**，但更擅长**重复执行已确认的流程**

你之前说的这一点非常关键：

> 首次用图像识别探索 UI → 固化流程 → 后续不再感知

这是 AI-Friendly 的**标准模式**。

**抽象为三阶段：**

1. **Exploration Phase（高 token / 高自由）**
2. **Extraction Phase（生成确定性流程）**
3. **Execution Phase（低 token / 低自由）**

架构必须**允许阶段切换**，而不是把探索逻辑写死在执行逻辑里。

---

### 公理 3：**可验证优先原则（Verifiability First）**

> AI 的输出如果不能被自动验证，那么就是“幻觉风险源”

所以系统设计时要问的不是：

* “AI 能不能写出来？”

而是：

* “我如何**自动判断 AI 写的是对还是错**？”

---

## 三、五层架构方法论（核心框架）

这是**AI-Friendly Code Architecture 的骨架**。

---

### Layer 1：Deterministic Core（确定性核心）

**特点**

* 无副作用
* 无 I/O
* 无环境依赖
* 同样输入 → 永远同样输出

**作用**

* 这是 AI **最安全、最稳定**的工作区域
* 可被无限次重写、重构、验证

**示例**

* 业务规则
* 数据变换
* 状态机
* 策略选择逻辑

> 原则：**90% 的复杂度应该被压进这一层**

---

### Layer 2：Explicit Contracts（显式契约层）

> AI 不擅长“猜接口”，但非常擅长“遵守规范”

**形式**

* TypeScript types / Zod / OpenAPI
* JSON Schema
* .spec.ts
* Protocol Definition（你之前问到的 spec 文件）

**关键要求**

* 输入、输出、错误都必须结构化
* 禁止“返回 null 表示很多种情况”

---

### Layer 3：Orchestration Layer（流程编排层）

这是 **AI 最容易出错的层**，也是最需要架构约束的层。

**设计原则**

* 线性流程 > 隐式回调
* 显式步骤编号
* 每一步都可独立验证

**非常适合**

* 状态机
* DAG
* Step Runner
* Playbook / Workflow DSL

> 多 Agent 系统，**只能在这一层活动**

---

### Layer 4：Integration Shell（不确定性交互层）

这里包括：

* UI
* 浏览器自动化
* 网络
* 文件系统
* 第三方 API

**AI 处理策略**

* 不“理解”它
* 只“驱动”它

也正是你说的：

* 首次：用视觉 / 感知
* 之后：用 selector / protocol

---

### Layer 5：Verification & Feedback Layer（验证与反馈）

**这是 AI-Friendly 架构的“护城河”**

必须存在：

* 自动化测试
* UI 回放
* Snapshot
* Golden Case
* Trace / Log / Artifact

> AI 不需要“知道哪里错了”，
> 只需要**被告知：这里失败了 + 证据**

---

## 四、AI-Friendly 的工程约束（Checklist）

### 代码层面

* 单文件职责单一
* 文件长度 < 300 行
* 函数 < 50 行
* 无隐式全局状态
* 不跨层访问

### 目录层面

* 目录名即语义
* 不用“utils / common”
* 按职责而不是技术分层

### 变更层面

* 每次修改范围小
* AI commit 可回滚
* 必须有验证入口

## 五、与传统架构思想的区别

## 一、哪些几乎完全等同于人类 best practices（只是变得更刚性）

这些东西在“人类时代”就被视为 best practice，只是很多团队属于“能做就好”，现在一旦引入 AI，就从“建议”升级成“硬性前提”。

1. **高内聚、低耦合**

   * 单一职责、清晰边界、分层架构
   * 人类靠脑补还能应付，AI 一旦遇到“这个函数顺带做三件事”，出错率暴涨

2. **强类型 / 明确数据模型**

   * TypeScript、protobuf、JSON Schema 之类
   * 以前是“减少人类 bug”，现在是“直接定义 AI 的思维边界”

3. **纯函数 / 无副作用核心**

   * 本来是为了测试性、可推理性
   * 对 AI 而言，这是少数能做到“几乎不会 hallucinate 的区域”

4. **自动化测试 / CI / 回归验证**

   * 以前防的是人类误改
   * 现在变成“防 AI 带来的海量小改动”的**唯一安全阀**

5. **清晰的错误处理与日志**

   * 好日志→以前是为了方便人 debug
   * 现在好日志→是给 AI Agent 提供**可消费的反馈信号**

简单说：
过去很多团队是“知道这么做更好，但没做到”；
AI 进场之后，**不这么做就根本玩不转**。

---

## 二、优先级发生了明显变化的点（“不是新的，但地位变了”）

这些也是传统 best practice，但 AI 出现后，**优先级被大幅提升**：

1. **机器可读性 > 人类可读性**

   * 以前：注释 / README 长篇人话也没问题
   * 现在：更偏好**结构化信息**（表格、JSON、schema、例子），方便 AI 直接 ingest

2. **稳定协议 > 炫技抽象**

   * 以前：可以接受为了“优雅”做一些复杂继承、多态设计
   * 现在：更看重的是**稳定、显式的协议与边界**，便于 AI 调用和组合

3. **一致性 > 灵活性**

   * 以前：可以为某些特殊场景开小口子做黑魔法
   * 现在：这种“个例”严重干扰 AI 的模式学习和行为预测

4. **可预测性 > 即时性能优化**

   * 以前：为了性能做各种 cache、隐式优化
   * 现在：更愿意牺牲一点点性能，换取更清晰可验证的行为

一句话：
很多老的 best practice 被**“拉上前台”**，变成架构的第一公民。

---

## 三、哪些是确实“专门为 AI 设计的东西”

这部分才是你说的“少数针对 AI 的设计”，但往往是方法论的“卖点”：

1. **Exploration → Freeze → Execute 模式**

   * 人类不会这么用：人类直接操作 UI + 写代码
   * AI-friendly 会显式支持：

     * 探索（感知 UI / 环境）
     * 冻结（抽象出稳定协议 / selector / DSL）
     * 执行（之后只走固定路径）
   * 这是典型的“人类不需要，但 AI 极其需要”的流程设计

2. **“给 AI 看”的工件**

   * Tool / API 的 JSON 描述
   * prompt 模板 / system spec / playbook
   * machine-friendly 的错误消息格式（code + structured detail）
   * trace / log 里明确 step、输入、输出，而不是“方便人 skim 的自然语言流水账”

3. **专门面向 LLM 的“接口层”**

   * 比如：

     * 一个 HTTP API 给人类客户端用
     * 但再包一层更简单、更约束的函数 / tool schema，给 LLM 用
   * 本质是：**把 LLM 当成一种很特殊的 SDK 使用者**

4. **AI 变更治理（AI Change Management）**

   * 例如：

     * AI 只能改某些目录（deterministic core）
     * 每次 AI 改动必须触发特定测试集 / sandbox 流程
     * 在 CI 里有针对 AI 改动的“额外 gate”（比如 golden case diff）
   * 这些在纯人类团队里一般不会这么精细地区分

5. **多 Agent 编排协议**

   * 定义好：每个 Agent 的职责、输入输出 schema、协作协议
   * 人类协作靠自然语言和默契就行
   * AI 协作则完全依赖这些**结构化的、机器可解析的协议**

## 四、你可以用来对外解释的一句话版本

给你几个可以对团队或外部讲的“简短说法”：

1. 面向内部团队：

   > 我们做的 **AI-Friendly 架构，不是推翻软件工程，而是把原来的 best practice 当作 AI 的“硬约束”来执行，再加上一层专门面向 LLM 的接口和验证机制。
   > 90% 是老原则，10% 是新工件和新流程。**

2. 面向更技术一点的同伴：

   > 可以把它理解为：

3. 面向产品 /业务侧：

   > 我们不是在搞一套新宗教，而是把软件写得更“结构化、可验证”，
   > 好处是：人写更不容易出错，AI 也能安全地参与研发和运维。

## 一、经典小黄鸭调试法的本质

先把“小黄鸭调试法”抽象到它的工程本质：

**你对小黄鸭做了什么？**

* 强迫自己**线性化思考**
* 把隐含假设**显性化**
* 用语言把“模糊直觉”变成“明确表述”
* 在表达过程中，自行发现逻辑漏洞

**小黄鸭本身：**

* 不理解
* 不反馈
* 不记忆
* 不执行

它的价值**100% 来自你自己**。

---

## 二、和 AI 讨论，发生了哪些本质升级

你已经敏锐地感受到：
**“和 AI 聊，能做得更进一步”**
这是对的，而且原因非常具体。

我用工程视角拆解差异。

---

### 1️⃣ 从「单向表达」升级为「双向结构化对齐」

| 维度   | 小黄鸭   | AI        |
| ---- | ----- | --------- |
| 信息流  | 单向    | 双向        |
| 思路结构 | 你负责   | AI 会反推、重排 |
| 隐含前提 | 你自己发现 | AI 会显式指出  |
| 逻辑断层 | 靠直觉   | 可被标注、质疑   |

**关键变化：**

> AI 会把你“说不完整的工程直觉”，强行变成**可对齐的结构**。

例如你在聊 AI-Friendly Architecture 时，其实多次发生过：

* 你说的是“感觉”
* 我给你还原成「原则 / 约束 / 反模式」

这是**外部结构化器（External Structuring Agent）**。

---

### 2️⃣ 从「思路澄清」升级为「可执行约束生成」

小黄鸭最多帮你想清楚：

> “啊，我原来是这个意思。”

AI 可以进一步做到：

* 把你的想法变成

  * 目录结构约束
  * API 边界
  * agent 分工
  * prompt 规范
  * CI / 测试策略

**也就是：**

> 从 *clarify thought* → *compile thought*

这一步，是工程化的质变。

---

### 3️⃣ 从「被动反思」升级为「主动反例驱动」

你应该已经注意到一个现象（尤其在架构讨论时）：

* 你提出一个设计
* AI 很自然地会：

  * 找边界情况
  * 提出反模式
  * 类比历史失败架构
  * 指出“AI 在这里容易出错”

这是小黄鸭**永远不可能做到的**。

这一步本质是：

> **自动引入第二视角 / 第三视角**

而不是你一个人脑内打转。

---

### 4️⃣ 从「即时对话」升级为「长期可累积的认知资产」

这是你现在正在做、但还没完全显性化的一点。

你并不是在“聊天”，而是在：

* 提炼方法论
* 形成可复用命名（AI-Friendly Code Architecture）
* 把思考结果准备喂给**未来的 AI**

这已经不是小黄鸭了，而是：

> **你在和一个“未来会复用这些结论的工程代理”对齐思维模型**

这一步，直接跨进了 **Agent-Oriented Engineering**。
